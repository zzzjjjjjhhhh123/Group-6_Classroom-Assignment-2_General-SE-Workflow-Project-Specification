# SE Workflow 原型 · 设计规格 → 任务分解 → 执行编排 → 可视化

课堂作业二要求的这一段流程的可运行原型：

```
产品设计规格(design spec) ──▶ 规格解析 ──▶ PM Agent 任务分解 ──▶ 依赖分析/编排器 ──▶ 依赖图 + 批次 + 状态可视化
        （输入）                    （结构化 spec）      （可审核的任务集）        （执行计划 + 生成依据）
```

**它不是一个"做微信/做小红书"的项目**，而是一套通用、可定制的 SE workflow 切片：
换产品只换一份规格文本，核心代码不改。仓库自带两份不同领域的规格作为测试案例。

## 快速开始

```bash
cd se-workflow
python app.py            # 打开 http://127.0.0.1:8000
```

- 只用 Python 3.9+ 标准库，**不需要 pip install**；
- 未配置 API Key 时自动走规则分解，**离线也能完整演示**；
- 想要大模型分解：在项目根建 `.env`，内容 `DEEPSEEK_API_KEY=sk-xxx`，重启即可（界面右上角会显示"LLM 已接入"）。

## 项目工作区

顶部「项目工作区」可创建多个本地项目，在项目中添加文本/代码文件、查看文件并保留对话历史。支持 Markdown、文本、JSON、Python、Web 前端、YAML、CSV 等文本格式；单个文件上限 1 MB。项目数据存放在运行目录的 `projects/` 下，默认不纳入 Git。

项目聊天使用当前配置的 DeepSeek 模型。只有用户勾选的项目文件会随当次消息发送给模型；未勾选的项目文件不会作为聊天上下文发送。模型未配置时，项目和文件管理仍可用，聊天会提示配置 API Key。项目资料和历史属于本机数据，删除项目目录即可清除。

### 规格输入格式

也可以先用自然语言描述产品想法。入口按「想法 → 多体讨论 → 建设方案 → 多方评价 → 人工确认 → DesignSpec」五步走：

1. **多体讨论**：商业分析、用户体验、技术挑刺、架构与方案四个角色各自发表观点，每条观点写明依据（引用想法原文）、风险内容、严重程度、触发条件以及是否需要人裁决。
2. **建设方案**：整理成 2–3 个可比较的方案（目标、核心能力、边界、风险、适用条件）。
3. **多方评价**：角色之间互相评价，记录支持与质疑、分歧点和风险；分歧并列呈现，不做平滑。
4. **人工确认**：点击卡片选定方案（规格按该方案重新生成），也可以暂缓或不采纳并留下理由；只有勾选确认后的规格才进入任务分解。决策记录与未决问题可一键导出为 Markdown。

配置了 DeepSeek 时讨论由模型生成；未配置时由行业模板生成并在界面上明确标注，模板同样不编造功能，用户选定后才继续。

支持 Markdown 和 JSON。Markdown 使用「项目目标、功能模块、非功能要求、约束、验收条件」章节；功能需求写在模块三级标题下的列表中，例如：

```markdown
# 产品：示例产品
## 项目目标
面向某类用户解决某个问题
## 功能模块
### 账号模块
- [P0] 用户可以注册并登录
## 非功能要求
- 页面在常见网络下 2 秒内完成加载
## 约束
- 使用 Web 技术实现
## 验收条件
- 用户能够完成注册、登录和退出
```

JSON 对象支持 `product`、`goal`、`modules`（模块含 `name` 和 `requirements`）、`non_functional`、`constraints`、`acceptance` 字段。新增产品时添加一份符合该格式的规格文本即可，不需要修改流程代码。

## 演示脚本（对应验收标准）

| 步骤 | 操作 | 应当看到 |
|---|---|---|
| 0 | 在一个空项目里输入一句想法（如「帮老旧小区做电梯加装协调：住户投票、费用分摊、进度公示」）→ 整理并给出选项 | 四个角色的观点清单（每条带依据/风险等级/触发条件/是否需裁决）、2–3 个可比较方案、多方评价记录（含质疑）、未决问题 |
| 0.5 | 点选另一个方案，或对某方案点「暂缓/不采纳」并填理由 | 规格按所选方案重新生成；决策记录增加一条，可导出为 Markdown |
| 1 | 点左侧「案例A：社区内容 App」→ 解析并分解 | 5 个模块、16 条需求、39 条任务，需求覆盖率 100% |
| 2 | 在「规格解析」页点任一需求行的「查看影响」 | 显示直接关联任务、依赖下游、受影响工作量和关键路径任务；对应任务与 DAG 节点高亮 |
| 3 | 切到「任务分解」页 | 每条任务带描述/交付物/验收标准/依赖/建议角色/规格出处；可改角色、人日、优先级、依赖 |
| 4 | 点「按新策略重新编排」，策略换「并行最大化」 | 批次数量与并行宽度变化，页面列出计划版本差异 |
| 5 | 切「编排与可视化」 | 依赖图（按拓扑层排布、红线为关键路径）+ 批次泳道 + 阻塞清单 + 编排依据 |
| 6 | 点「演练推进」 | 按批次逐条产生状态事件，节点置灰，事件流可回放 |
| 7 | 依次换成案例B/C：19 条需求 → 43 条任务、29 条需求 → 64 条任务 | **代码零修改**，同一套流程跑三个不同领域 |
| 8 | 切「运行与复盘」→ 选一条记录 → 查看复盘 | 指标卡（总耗时/模型占比/人工等待/失败与重排）、计划 vs 实际偏差表、四类归因、改进建议与完整 Markdown 报告 |
| 9 | 点「回放到事件流」 | 按 seq 顺序重放历史事件，任务状态逐条点亮——同一份数据可换视角反复看 |

## 关键机制（这几条是答辩时最容易被问的）

1. **可追溯**：每条任务必须引用规格里真实存在的需求编号（`source_refs`），界面上点任务能看到"出自哪一节哪一行哪句原文"。
2. **不猜**：任务若没有出处、缺交付物或缺验收标准，一律降级为「待确认」，**不会进入执行批次**；规格里的缺失/歧义（"等""待定"、模块无需求）会生成待确认问题。LLM 返回内容会按必需字段和类型检查；格式不合格时退回规则分解。
3. **拒绝非法计划**：所有循环依赖都会被完整检出（按强连通分量分组，含多条互不相交的环），环上任务、依赖不存在任务或依赖自身的任务一律被阻止进入计划，界面给出环路分组与修正提示。
4. **编排可解释**：每个批次都写明"为什么这样排"（第几层、依赖已满足、受并行上限切片），并给出关键路径与工期下界、每个任务的总时差（能拖几天不影响总工期）和冗余依赖提示（可被传递覆盖、删掉不影响排期的直接依赖）。
5. **可定制**：粒度、策略、并行上限、单角色并行上限都可调，同一份任务集能排出不同计划。初次运行会给出计划预览；人工改任务后可重新编排并对比计划差异。
6. **重复提示范围**：当前只提示同模块下标题完全相同的任务，不做语义去重，也不自动合并任务。
7. **需求影响可追踪**：选中一条需求后，沿 `source_refs` 找出直接关联任务，再沿 `depends_on` 递归查找下游任务；页面汇总受影响任务数、估算工作量、关键路径数量和所在批次，并同步高亮任务表与 DAG。该分析依据现有任务和依赖关系，不会自行编造需求变更后的新任务。
8. **建议不等于确认**：想法入口的讨论、方案、评价全部是「建议」，只有用户点选方案并勾选确认后，内容才写入 DesignSpec；暂缓/不采纳会连同理由记入决策记录，可导出留档。风险一律带严重程度、触发条件和是否需人裁决，缺级别的不会被自动补一个。
9. **链路可观测**：每次“想法→讨论→规格”或“分解→编排”都会生成 12 位 `trace_id`，逐次记录模型调用的名称/耗时/成败（失败降级也留痕），随项目快照持久化（最近 20 条），界面配置栏下方的链路追踪条实时展示；这就是多智能体工作流“可观测性”的落地：看得见、查得清、算得出。
10. **讨论会收敛（chatmanager 式）**：第二轮每个角色必须点名回应其他角色的观点（支持/反驳/补充，反驳需给理由与替代建议），主持人汇总出共识点、保留分歧（含各方立场与收敛方式）并给出推荐方案；建议可一键采纳进决策记录。模型收敛为主路径，评价记录投票归纳为规则兑底，收敛方式会在界面上标明。
11. **实现阶段闭环**：可开关“评审任务”（默认关，保持已演练的批次数字稳定）；打开后每个模块在联调测试后自动追加评审任务，编排图呈现编码→测试→评审的分层闭环，评审交付物为评审结论 + 问题清单。
12. **编排动态化**：演练推进可一键“注入失败→动态重排”：失败任务自动纳入返工并重排其下游，已完成任务不再排期，系统按当前策略重新分批并逐条列出与失败前计划的差异——这就是“执行中出问题→计划自动演化”的动态闭环。
13. **可观测底座（Run / Span / Event）**：每次执行是一个 `run`，阶段是 `span`，过程是严格递增的 `event`；事件只追加不修改，落 `projects/<id>/runs/<run_id>/{run.json, events.jsonl, artifacts/}`，零数据库依赖。埋点覆盖想法、收敛、解析、分解、质量、编排、执行、重排与人工决策九类，`seq` 连续可回放。
14. **复盘能力（指标 / 偏差 / 归因 / 建议）**：任一历史 run 可一键生成复盘报告——阶段耗时瀑布、模型与人工占比、计划 vs 实际偏差表（批次/任务/失败/重排）、四类归因、可直接执行的改进建议，并可导出 Markdown。界面“运行与复盘”页支持选择记录、查看报告、回放到事件流。
15. **人工等待被量化**：闸门确认（G1 想法确认 / G3 计划审批 / G4 失败处置）的等待时长随 `gate.pass` 事件记录；当等待超过运行时长时，归因会明确写出“流程实际周期由人决定”，而不是把人的时间吞进总耗时。

## 可配置项

| 类别 | 参数 | 取值 | 影响 |
|---|---|---|---|
| 分解粒度 | `granularity` | 粗 / 中 / 细 | 粗=按模块合并（任务少、颗粒大），中=按需求，细=需求×层 |
| 分解规则 | `split_non_functional` | 开/关 | 非功能需求是否单独出工程化任务 |
| 分解规则 | `auto_test_task` | 开/关 | 是否每模块生成联调用例任务 |
| 分解规则 | `auto_review_task` | 开/关 | 是否每模块追加评审任务（编码→测试→评审闭环；默认关） |
| 分解规则 | `role_pool` | 角色列表 | 任务只派给团队里真实存在的角色 |
| 估算范围 | `min_estimate_days` / `max_estimate_days` | 0.5–2 人日 | 单任务估算边界；界面编辑也遵循此范围 |
| 编排 | `strategy` | 依赖优先 / 并行最大化 / 角色批量 / 关键路径优先 | 决定批次划分方式 |
| 编排 | `max_parallel` | 1–8 | 每批最多并行任务数 |
| 编排 | `per_role_wip_limit` | 0–8 | 一个角色同时最多承担几个任务（0=不限） |

## 目录

```
se-workflow/
├─ app.py            Web 服务（标准库 http.server）+ 接口
├─ pipeline.py       主链路：解析→分解→质量→编排，事件流，计划版本差异
├─ spec_parser.py    规格解析（Markdown / JSON）→ DesignSpec + 待确认问题
├─ pm_agent.py       PM Agent：LLM 主路径 + 规则兜底 + 覆盖率补洞
├─ graph.py          依赖图：全环检测（强连通分量）、拓扑分层、关键路径、任务时差、冗余依赖、孤立任务
├─ orchestrator.py   编排器：4 种策略、阻塞判定（待确认/环/依赖缺失）与传导、编排依据
├─ contracts.py      唯一契约源：数据结构 + 校验 + 需求覆盖检查
├─ config.py         可配置项与 LLM 配置
├─ llm.py            DeepSeek 客户端（urllib，无第三方依赖）
├─ observability.py 可观测底座：Run / Span / Event + Run Store（runs/<id>/events.jsonl）
├─ metrics.py       复盘分析：指标聚合、计划偏差、耗时归因、改进建议、Markdown 报告
├─ web/index.html    单页可视化（原生 JS，自绘 SVG 依赖图 + 运行与复盘页）
├─ docs/            可观测框架设计（六层结构、事件规范、分工、里程碑）
├─ examples/         三份不同产品的样例设计规格
└─ tests/            49 条自测（python -m unittest discover -s tests -v）
```

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/config` | 策略、粒度预设、LLM 是否可用 |
| GET | `/api/examples` `/api/example?file=` | 样例规格列表 / 原文 |
| POST | `/api/run` | `{spec_text, decompose, orchestrate, project_id?}` → spec + tasks + plan + coverage + events + trace |
| POST | `/api/reorchestrate` | `{spec, tasks, orchestrate}` → 新计划 + 版本差异（人工审核后重排） |
| POST | `/api/simulate` | `{tasks, plan, fail_task_ids?, run_id?}` → 演练推进的状态事件（同时写入 Run Store） |
| POST | `/api/replan` | `{spec, tasks, plan, failed_task_ids, done_task_ids, orchestrate, run_id?}` → 动态重排 + 计划差异（续写同一 run） |
| GET | `/api/runs?project_id=&limit=` | 运行记录列表（新→旧；不传 project_id 则跨项目列出） |
| GET | `/api/run?id=` | 单次运行：元信息 + 事件流（最近 300 条）+ 指标 + 偏差 + 归因 + 建议 |
| GET | `/api/review?id=` | 同上，另含可直接交付的 Markdown 复盘报告 |
| POST | `/api/run/event` | `{run_id, type, stage, actor, data, finish?}` → 人工事件入观测（`human.* / gate.* / task.* / anomaly`） |
| GET | `/api/projects` `/api/project?id=` | 项目列表 / 项目资料、聊天历史与链路追踪（`traces`） |
| GET | `/api/project/file?id=&name=` | 读取项目中的单个文本文件 |
| POST | `/api/projects` | `{name}` → 创建本地项目 |
| POST | `/api/project/files` | `{project_id, name, content}` → 保存文本文件 |
| POST | `/api/project/chat` | `{project_id, message, context_files}` → 项目对话并保存历史 |

需求影响分析在前端基于当前 `spec`、`source_refs`、`depends_on` 和计划批次即时计算，不新增模型调用或服务端接口。

## 与整条 SE workflow 的关系

```
作业1（需求/设计规格产出）──▶ 【作业2：本原型】设计规格 → 任务分解 → 编排 → 可视化 ──▶ 作业3（任务执行 / Agent 执行）
                                      ▲ 只做这一段，不实现具体产品
```

红蓝评审、PRD 会签、门禁等属于完整流程的其他分段，本原型只把它们当作后续扩展点。

## 已知限制

- 规则分解基于关键词与模块结构，对文风极不规范的规格会退化成"每需求一条后端任务"；LLM 路径可缓解。LLM 结果使用代码内必需字段/类型检查，不使用独立 JSON Schema 校验库。
- 当前重复任务检查只比较同模块内完全相同的标题，不识别语义重复，也不识别并保留冲突方案。
- 工期估算由任务类型给出基准值再按粒度缩放，不与具体团队产能挂钩（可后续接入人员日历）。
- 「演练推进」是演示用推演，按批次产生事件，不代表真的执行了开发任务。
- 计划版本差异记录在内存中，服务重启后清空。
- 运行记录每个项目默认保留最近 30 条（滚动清理）；执行推进仍是演示推演，不接真实 CI。
- 复盘建议是规则推断（基于覆盖率、失败、并行度、人工等待），不是模型生成；因此只给方向与做法，不自动改配置。
