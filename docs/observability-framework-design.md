## 0. 一句话定位

**让一条「想法 → 需求 → 任务 → 计划 → 执行 → 复盘」的软件工程流水线，跑过之后能被完整看见、能被人干预、能被重新播放、并且能反过来改自己下一次怎么跑。**

对应四个关键词：**采集（看得见）→ 呈现（看得懂）→ 交互（管得住）→ 复盘（改得动）**，外加一层 **定制（不同项目跑不同流程）**。

## 1. 现状盘点：作业 1 / 2 已经给了我们什么

| 能力 | 现状 | 落在哪里 | 观测视角下的缺口 |
|---|---|---|---|
| 想法 → 多角色讨论 → 方案 → 评价 → 确认 | 已实现（LLM 主路径 + 规则兜底，含第二轮收敛与共识决策） | `idea_to_spec.py`、`app.py:/api/draft-spec` | 讨论过程只存在于返回的 JSON 里，不入库、不可跨会话比较 |
| 规格解析（需求编号、出处、待确认问题） | 已实现 | `spec_parser.py` | 解析耗时、缺失项数量未留痕 |
| 任务分解（LLM + 规则兜底 + 覆盖率补洞） | 已实现 | `pm_agent.py`、`llm.py` | 每次调用耗时已记 trace，但**质量口径**（覆盖率、待确认数）未随 run 落盘 |
| 依赖分析与编排（环检测/分层/关键路径/4 策略/批次） | 已实现 | `graph.py`、`orchestrator.py` | 编排依据只作为文本理由返回，未结构化为可对比指标 |
| 可视化（三屏、DAG、泳道、关键路径、阻塞清单） | 已实现 | `web/index.html` | 只有「计划视图」，没有「实际执行视图」，也没有时间维度的回放 |
| 演练推进 + 失败注入 → 动态重排 | 已实现 | `pipeline.py:/api/simulate`、`/api/replan` | 事件是临时的，播完即丢；重排前后的因果链没有留存 |
| 链路追踪 | 已实现（12 位 trace_id + 每次调用耗时/成败） | `app.py` 的 `_new_trace` / `_persist_trace` | 只有 trace 粒度，没有 span 层级；只存最近 20 条，不能按 run 检索与回放 |
| 人工决策记录 | 已实现（确认/暂缓/不采纳 + 理由，可导出） | `web/index.html` | 决策未与「执行结果」关联，无法回答"这个决定后来对不对" |
| 项目配置（粒度/策略/并行/角色池/评审开关） | 已实现 | `config.py`、项目快照 | 配置是「一次性参数」，缺少"按项目类型成套下发"的模板层 |

**结论：素材很足，缺的是「统一的数据底座 + 时间维度 + 因果关联」。** 现在的可视化是"计划长什么样"，不是"过程发生了什么"。

三处核心缺口，正好对应本次要做的事：

1. **观测数据没有统一模型**：trace 是个字典，事件是临时数组，决策在另一个字段——三者无法按一次运行串起来。
2. **没有回放能力**：刷新页面就只剩最后状态，看到的是快照而不是过程。
3. **没有反馈闭环**：复盘结论停在人脑子里，不会变成下一次的配置或模板调整。

## 2. 总体框架：六层

```
┌──────────────────────────────────────────────────────────────┐
│ L5 复盘层  回放 · 偏差分析 · 归因 · 改进建议 · 复盘报告导出      │
├──────────────────────────────────────────────────────────────┤
│ L4 呈现层  实时过程视图 · 计划视图 · 执行视图 · 指标看板         │
├──────────────────────────────────────────────────────────────┤
│ L3 交互层  闸门确认 · 参数调整 · 失败注入 · 任务接管 · 回放控制   │
├──────────────────────────────────────────────────────────────┤
│ L2 存储层  Run Store：run.json + events.jsonl + artifacts       │
├──────────────────────────────────────────────────────────────┤
│ L1 采集层  Span/Event 埋点：想法·解析·分解·编排·执行·人工决策     │
├──────────────────────────────────────────────────────────────┤
│ L0 定制层  WorkflowTemplate：项目类型 → 阶段序列/闸门/角色/策略   │
└──────────────────────────────────────────────────────────────┘
        ↑                                              │
        └────────── 复盘结论转化为模板/参数调整 ←────────┘
```

设计取舍说明（答辩时会被问）：

- **为什么用 append-only 事件日志而不是数据库？** 零依赖、可 diff、可回放；事件只追加不修改，天然满足"事后追溯"的审计要求。出问题的永远是"最后一条事件的状态"，可复现。
- **为什么 run 与 project 分离？** 一个项目会跑很多次（换想法、换方案、换参数），复盘要能横向比较"同一项目的第 1 次和第 5 次"，所以 run 是一等公民，project 只是容器。
- **为什么模板也是一等公民？** 定制不能靠"改代码"，要让"用了哪个模板、哪个版本、覆盖了哪些参数"进入 run 记录，否则复盘无法区分"流程本身有问题"还是"这次参数没调好"。

## 3. 数据模型（这是整个框架的地基）

### 3.1 四个核心对象

| 对象 | 含义 | 关键字段 |
|---|---|---|
| **Run** | 一次完整流水线执行 | `run_id`、`project_id`、`template_id@version`、`config` 快照、`status`、`started_at/finished_at`、`summary`（派生指标） |
| **Span** | 一个阶段的耗时区间（可嵌套） | `span_id`、`parent_span_id`、`stage`、`actor`（role/agent/human）、`start/end`、`status`、`attrs` |
| **Event** | 过程里发生的一件事 | `seq`（严格递增）、`ts`、`run_id`、`span_id`、`type`、`actor`、`payload` |
| **Decision** | 人工决策（可审计） | `decision_id`、`stage`、`type`（确认/暂缓/不采纳/重排/接管）、`reason`、`by`、`ts`、`linked_event_seq` |

### 3.2 事件类型表（采集规范，全员按此埋点）

| 分组 | type | 触发点 | 必填 payload |
|---|---|---|---|
| 生命周期 | `run.start` / `run.end` / `run.fail` | 一次 run 开始/结束 | `template_id`、`config`、`status` |
| 阶段 | `stage.start` / `stage.end` | 每个阶段进入/退出 | `stage`、`actor`、`duration_ms`、`ok` |
| 模型 | `llm.call` / `llm.fail` / `llm.fallback` | 每次大模型调用 | `name`、`model`、`duration_ms`、`ok`、`error?` |
| 产物 | `artifact.produced` | 规格/任务/计划等产物生成 | `kind`、`ref`、`count`、`quality`（覆盖率等） |
| 人工 | `human.decision` / `human.edit` | 确认、暂缓、改任务、调参数 | `decision_id`、`type`、`reason` |
| 闸门 | `gate.enter` / `gate.pass` / `gate.reject` | 阶段间人工闸门 | `gate`、`wait_ms` |
| 执行 | `task.start` / `task.done` / `task.fail` / `task.blocked` / `task.retry` | 执行推进 | `task_id`、`batch`、`role` |
| 重排 | `replan.trigger` / `replan.done` | 失败或人工触发重排 | `cause`、`failed_ids`、`diff_count` |
| 异常 | `anomaly` | 覆盖率不足、依赖环、超长任务 | `code`、`detail` |

**规范**：`seq` 由服务端单点分配（保证回放顺序）；`ts` 用 ISO8601；`actor` 必须标明是人还是哪个角色，否则复盘时分不清"机器慢"还是"人慢"。

### 3.3 存储布局（零依赖，文件系统即可）

```
projects/<project_id>/
  project.json                  # 项目资料（已有）
  runs/
    <run_id>/
      run.json                  # Run 摘要 + 派生指标 + 复盘结论
      events.jsonl              # 一行一条事件，append-only
      artifacts/
        spec.json  tasks.json  plan_v1.json  plan_v2.json
```

保留策略：每个项目留最近 30 个 run，超出按时间滚动删除（`run.json` 里的 `pinned` 可保护演示用的关键 run）。

## 4. 采集层：埋点怎么落到现有代码

原则：**不改业务逻辑，只在阶段边界与外部调用处插桩**。已有 `_new_trace/_record_llm_call` 演进为 `Span` 树。

| 埋点位置 | 现有函数 | 要加的事件 |
|---|---|---|
| 入口编排 | `pipeline.Pipeline.run` | `run.start` → 每阶段 `stage.start/end` → `run.end` |
| 规格解析 | `spec_parser.parse_spec` | `stage.end`（含需求数、待确认数、耗时） |
| 分解 | `pm_agent.decompose` | `llm.call`（已有）+ `artifact.produced`（tasks 数、覆盖率、待确认数）+ `llm.fallback` |
| 质量校验 | `contracts.validate_tasks / check_coverage` | `anomaly`（未覆盖需求、缺出处、超期任务） |
| 依赖与编排 | `graph.py` / `orchestrator.plan` | `stage.end`（层数、边数、关键路径长度）+ `artifact.produced`（plan 版本） |
| 执行推进 | `pipeline.simulate` | `task.*` 逐条事件（已有形态，改为写 Run Store） |
| 重排 | `pipeline.dynamic_replan` | `replan.trigger/done` + 计划 diff |
| 前端交互 | `web/index.html` 各按钮 | `human.*`（选方案、确认、改任务、调参数、注入失败） |

新增统一入口：`observability.py`（约 200 行，纯标准库）

- `RunRecorder`：`start_run() / span(stage) / emit(type, **payload) / end_run()`，线程安全，写 jsonl 同时更新内存摘要
- `Span`：上下文管理器，`with rec.span("decompose", actor="pm-agent") as s: ...`
- `metrics.py` 派生指标：阶段耗时占比、人工等待占比、LLM 调用成功率、返工率、覆盖率、关键路径偏差

## 5. 呈现层：三类视图 + 一块看板

| 视图 | 内容 | 复用/新增 |
|---|---|---|
| **过程视图**（已有三屏） | 规格 / 任务 / 计划；DAG、泳道、关键路径、阻塞清单 | 复用作业 1/2，补"阶段条"显示当前处在哪一步 |
| **执行视图**（新增） | 批次时间轴甘特：每任务实际开始/结束、失败标记、重排后的新批次叠加显示 | 新增：时间轴 + 计划 vs 实际双条对比 |
| **追踪视图**（升级现有 trace 条） | Span 树瀑布图：想法（20s）→ 收敛（8s）→ 解析（0.1s）→ 分解（0.03s）→ 编排（0.01s），人工等待单独一段 | 新增：瀑布图（SVG，无需第三方库） |
| **指标看板**（新增） | 阶段耗时占比、LLM 调用次数/成功率、人工等待时长、任务完成率、返工次数、覆盖率、关键路径长度 | 新增：小卡片 + 迷你条形图 |

设计要点：**同一份 Run 数据支撑三个视图**，视图之间可互相跳转（点瀑布图的"分解"段 → 执行视图高亮对应任务）。这体现"一套观测数据、多种呈现"，也是与"三个页面各画各的"最本质的区别。

## 6. 交互层：闸门与干预

### 6.1 四道闸门（把"人怎么参与"变成可观测对象）

| 闸门 | 位置 | 通过条件 | 事件 |
|---|---|---|---|
| G1 想法确认 | 讨论 → 规格 | 用户勾选确认 | `gate.pass` + `human.decision` |
| G2 方案选型 | 多方案 → 规格重生成 | 选定一个方案 | `human.decision` |
| G3 计划审批 | 编排 → 执行 | 用户确认可执行 | `gate.pass` |
| G4 失败处置 | 执行中失败 | 返工/跳过/降级/终止 | `human.decision` + `replan.trigger` |

所有闸门的**等待时长**都要记（`wait_ms`）——这是复盘里最有说服力的数字之一："这次流水线机器只跑了 28 秒，人等了 6 分钟。"

### 6.2 执行期干预

| 干预 | 已有 | 要补 |
|---|---|---|
| 改任务再重排 | ✅ | 记录 `human.edit` + 前后 diff |
| 注入失败 → 自动重排 | ✅ | 把"人注入"与"真失败"区分开（`cause=injected/manual`），复盘时不混淆 |
| 暂停/继续 | ❌ | 新增：暂停后事件仍入队但标记 `paused`，回放可见"这里停过" |
| 任务接管 | ❌ | 新增：标记某任务由人完成（`actor=human:<name>`），用于对比"人做的 vs 推演做的" |
| 调参重跑 | 部分 | 每次 run 记录 config 快照，支持"同想法 + 不同参数"横向对比 |

## 7. 复盘层（这是最能拉开差距的一块）

### 7.1 四类复盘动作

1. **回放（Replay）**：按 `seq` 顺序重放事件，界面有播放/暂停/进度条/倍速；回放时三个视图同步（甘特上任务逐条点亮、瀑布图高亮当前阶段）。技术上就是"读 jsonl → 定时吐事件"，不需要录屏。
2. **偏差分析（Plan vs Actual）**：计划批次/工期/角色负载 vs 实际执行结果，输出偏差表：
   - 批次偏差（计划 15 批 / 实际 17 批，+2 因返工）
   - 工期偏差（计划 47 人日 / 关键路径 12 天 vs 实际完成顺序）
   - 角色负载偏差（谁被塞爆了）
3. **归因（Why）**：沿依赖链回溯失败影响面——`T12 失败 → 下游 5 条受阻 → 触发重排 → 新增 2 批`，用因果链图展示；自动归类"这次延误来自：模型等待 / 人工等待 / 返工 / 依赖串行"。
4. **改进建议（Next）**：根据归因生成可执行建议，例如
   - "并行上限 3 时批次数 15，调到 5 可压到 9 批，但角色 qa 负载超限 → 建议先加人再加并行"
   - "本类项目（小程序）在'规格解析'阶段平均 0.1s，但讨论阶段平均 24s，建议模板里给讨论设 2 轮上限"
   - "3 次运行中有 2 次在'评审任务'开启后总批次增加 4 批，建议仅对高风险模块开启"

### 7.2 复盘报告（可导出 Markdown，交付/答辩直接用）

```
# Run 复盘报告 · <project> · <run_id>
1. 概况：模板/配置/总时长/闸门等待
2. 阶段耗时瀑布
3. 计划 vs 实际偏差表
4. 关键事件时间线（失败、重排、人工决策）
5. 归因结论（四类耗时占比）
6. 改进建议（3 条，带可点击的"应用此建议"）
7. 与同项目历史 run 的对比（第 N 次 vs 第 N-1 次，好在哪里）
```

**闭环的关键**：报告里的"应用此建议"不是文字，而是**一键把参数/模板改动写进下一次 run 的配置**，这样"通过执行案例优化 wf"就有了机制化落地，而不是靠人记。

## 8. 定制层：不同项目跑不同流程

### 8.1 模板模型

```jsonc
{
  "template_id": "web-app", "version": "1.2", "label": "Web 应用（标准七阶段）",
  "stages": [
    {"key": "idea",    "actor": "multi-agent", "gate": "G1", "required": true},
    {"key": "spec",    "actor": "parser",      "gate": null},
    {"key": "decompose","actor": "pm-agent",   "gate": null},
    {"key": "plan",    "actor": "orchestrator","gate": "G3"},
    {"key": "execute", "actor": "executor",    "gate": "G4"}
  ],
  "roles": ["pm", "backend", "frontend", "qa", "devops"],
  "defaults": {"granularity": "medium", "strategy": "dependency_first",
               "max_parallel": 3, "auto_test_task": true, "auto_review_task": false},
  "rules": {"min_modules": 3, "require_source_refs": true,
            "acceptance": ["每个模块必须有验收标准"]}
}
```

### 8.2 内置四类模板（覆盖"不同项目类型"的论证）

| 模板 | 阶段差异 | 角色差异 | 默认策略 | 适用 |
|---|---|---|---|---|
| `web-app` 标准 Web 应用 | 七阶段全开 | 含 devops | 依赖优先 / 中粒度 | 作业 1/2 的案例 A/B/C |
| `mini-program` 小程序 | 执行后加「审核发布」阶段 | 含 ops-review | 关键路径优先 | 有平台审核约束的项目 |
| `data-pipeline` 数据/算法 | 「规格」前加「数据准备」，执行后加「评测」 | data/算法角色替换 frontend | 并行最大化 | 数据集、模型类项目 |
| `course-hw` 课程作业（轻量） | 只到「计划」为止，不执行 | 单人角色 | 依赖优先 / 粗粒度 | 只需要排期的场景 |

### 8.3 定制不等于改代码

- 界面：选模板 → 看到阶段序列与默认参数 → 按需覆盖（粒度、策略、并行、评审开关、角色池）→ 保存为项目级 workflow
- 模板也参与可观测：`run.json` 记录 `template_id@version` 与**全部生效参数**，复盘时可做"同项目换模板前后对比"
- 自定义模板：允许复制内置模板改 JSON（阶段增删、闸门位置、验收规则），存到 `templates/<id>.json`，无需改 Python

## 9. 端到端串联（完整闭环长什么样）

```
[模板选择] → 想法 → 讨论收敛 → [G1/G2] → 规格 → 分解 → 编排 → [G3] → 执行
                                                                   ↓
                                                    失败/人工干预 → [G4] → 自动重排 → 继续执行
                                                                   ↓
                                       Run Store（事件全留痕）→ 过程/执行/追踪三视图 + 看板
                                                                   ↓
                            复盘（回放 + 偏差 + 归因 + 建议）→ 一键应用 → 下一次配置/模板
```

**"通过执行案例优化 wf"的验证方式**：同一个想法跑 3 次——基线 / 按复盘建议调参 / 换模板，把三次的批次数、总工期、人工等待、覆盖率做成对比表。这是最有说服力的实验设计。

## 12. 演示脚本（5 分钟，讲给老师）

1. **30s｜定位**：一句话说清"可观测 = 看得见 + 管得住 + 可回放 + 能改进"。
2. **60s｜定制**：选 `mini-program` 模板 → 界面上的阶段序列与默认参数随模板变化 → 说明"不同项目类型跑不同流程，不改代码"。
3. **90s｜跑一遍**：输入一个陌生想法（如"社区旧书漂流角"）→ 讨论收敛 → 确认 → 规格 → 分解 → 编排 → 审批 → 执行；全程指着瀑布图说"这一段是模型 20 秒，这一段是规则 30 毫秒，这一段是人在等"。
4. **60s｜干预**：注入一次失败 → 下游受阻 → 自动重排 → 甘特上出现新批次并标红，说明"计划不是一次算死的"。
5. **60s｜复盘**：打开复盘报告 → 偏差表（计划 15 批 / 实际 17 批）→ 归因（+2 批来自返工）→ 建议"并行上限 5 + 评审只对核心模块开" → 点"应用建议" → 重跑一次 → 批次数下降，对比表出现。
6. **30s｜收尾**：强调闭环——"观测不是为了好看，是为了让流程下一次跑得更好"。

## 13. 风险与答辩预案

| 会被问 | 怎么答 |
|---|---|
| 这不就是日志系统吗？ | 日志是给开发者看文本；我们做的是**结构化事件 + 因果关联 + 计划偏差 + 可回放**，服务对象是项目管理者，输出是决策建议。 |
| 执行是真的在跑代码吗？ | 现阶段执行是**推演 + 人工接管**（明确标注 `simulate`）；框架已把 `actor=human/agent` 区分开，后续接真实 CI 只需替换 executor，事件契约不变。 |
| 回放和录屏有什么区别？ | 录屏是像素，回放是**数据**：可跳转、可按阶段过滤、可换视图看同一段时间、可与另一次 run 对比。 |
| 模板定制会不会失控？ | 模板有版本号、有校验规则（阶段必需项、闸门位置、角色合法性），且每次 run 记录生效模板版本，出问题能定位到"哪个模板的哪一版"。 |
| 只有三个案例，怎么证明通用？ | 用四类模板 + 三次对比实验（基线/调参/换模板）说明"同一套底座能适配不同流程"，而不是"只对三个样例调过参"。 |
